# Industry-Leading Color Engine Plan

> Historical implementation plan. It records the color-engine work and proof language that led to
> the current program, but it is no longer the execution or completion authority. Use
> `docs/color-engine-and-app-foundations-completion-strategy.md` for current status, ordering,
> deletion gates, evidence requirements, and release completion.

## Purpose

This was the execution contract for taking the color engine from a strong custom pipeline to
a professionally trustworthy system. It supersedes the implementation sequence in
`docs/color-science-roadmap.md`, whose original core-pipeline milestones are now largely complete.

The goal is not more controls. The goal is repeatable color from camera input through preview,
soft proof, and export, backed by authoritative transforms, measured tolerances, real photographs,
and bounded interactive performance.

## North-star pipeline

```text
encoded source / camera RAW
  -> authoritative source profile or camera characterization
  -> scene-linear wide-gamut working pixels
  -> scene-referred tone, color, layers, and local adjustments
  -> photographic rendering transform for target luminance and viewing conditions
  -> target-gamut mapping and display encoding
  -> monitor preview, soft proof, or profile-embedded export
```

The engine must keep these contracts distinct:

1. **Colorimetric transforms** reproduce a profile or standard accurately.
2. **Photographic rendering** maps scene appearance into a display's luminance and gamut.
3. **Creative grading** intentionally changes the photograph.

No stage may silently do the work of another.

### Remaining blockers

The implementation now has a single executable default-promotion decision. The
`photo-editor-color-default-promotion:v2` manifest revalidates every nested artifact, requires
distinct Darwin and Windows Release migration binaries, regenerates the licensed-corpus aggregate,
binds the complete evidence map by SHA-256, rejects a dirty or revision-mismatched checkout, and
requires two final approvers who are independent of the evidence preparers. Each approval is an
OpenSSH detached signature over the complete decision and must verify against an allowed-signers
file already committed at the recorded revision. Run it with:

```sh
python3 -B scripts/color/validate-color-default-promotion.py \
  /path/to/evidence/color-default-promotion.json \
  --repository-root . \
  --allowed-signers perf-corpora/color-validation-required/color-promotion-allowed-signers
```

The remaining unchecked items below therefore mean external evidence has not yet been collected;
they no longer indicate that a schema, validator, or final decision mechanism is missing.
`prepare-color-default-promotion.py` and `finalize-color-default-promotion.py` make that external
handoff deterministic: every input must already be inside one evidence volume, draft creation is
explicitly non-promoting, and final output is written only after both trusted detached signatures
and the complete nested validator pass.

### Components that should not be rewritten

- The layer/mask model and most creative adjustment APIs are not the core color-management problem.
- The recipe migration system already provides the compatibility mechanism needed for a new renderer.
- The preview/export call graph, cache ownership, cancellation, and telemetry should be preserved.
- The existing tests should be used as a migration safety net, not discarded because new reference
  tests are more rigorous.
- The current OKLCH output mapper should remain available for historical recipes until the new
  renderer has passed both reference and editorial gates.

### Safe replacement sequence

For every replaced subsystem:

1. Keep the current public facade and serialized state stable.
2. Add the new implementation beside the old implementation.
3. Run both implementations against identical pixels and emit perceptual/error reports.
4. Enable the new implementation behind a rendering-model version or explicit feature flag.
5. Promote it to the default only after reference, real-photo, parity, performance, and migration
   gates pass.
6. Keep the old implementation for legacy recipes.
7. Delete old code only when no supported recipe, cache artifact, or export contract depends on it.

## Standards and reference policy

Implementations must be checked against primary specifications or an independent reference engine.

- **Raster ICC:** ICC.1:2022 profile version 4.4 is the required baseline. Continue reading common
  v2 profiles for compatibility. Treat iccMAX/ICC.2 as a later extension, not a release blocker.
- **RAW/DCP:** Adobe DNG 1.7.1.0 defines the camera-profile and metadata behavior to reproduce.
  The specification is reference material only: production and conformance code must remain
  project-authored and must not call an Adobe API/SDK or consume Adobe-generated oracle fixtures.
- **Display rendering:** ACES 2 output-transform structure and Hellwig 2022 JMh gamut mapping are
  the primary reference model to evaluate. The product does not need to adopt ACES as its saved
  working space to learn from or match its rendering quality.
- **Interchange:** OpenColorIO 2.5-class CPU/GPU processors are the reference for optional
  scene-linear, display/view, CLF/CTF, and production-pipeline interoperability.
- **Platform oracles:** ColorSync on macOS and a pinned Little CMS build provide independent ICC
  comparison. The production cross-platform ICC backend should be Little CMS unless the Phase 1
  spike finds a measured correctness, licensing, or performance blocker.

Every external backend and reference configuration must be pinned by version and checksum in test
artifacts. Silent system-profile or config drift is a test failure.

The proprietary boundary is therefore explicit: Photo Editor owns the pipeline, recipes, fixtures,
oracles, validation contracts, processor selection, and product behavior. ICC, DNG, ACES, CIE, and
ITU documents define interoperable behavior; OpenColorIO, OpenImageIO, Little CMS, and LibRaw are
pinned open-source dependencies or independent test engines. No Adobe service, runtime API, SDK,
binary fixture generator, or private implementation is part of the color engine.

That boundary is now machine-enforced by `validate-proprietary-color-boundary.py`. It scans build
and package declarations for Adobe SDK dependencies, runtime source for Adobe DNG/XMP SDK headers,
symbols, and network endpoints, and color-fixture names plus structured provenance for Adobe-made
oracles. Its adversarial suite proves each forbidden route is rejected while allowing the `Adobe
RGB` interoperability name and public-DNG fields and legacy identifiers that must remain readable.

## Release metrics

These are initial gates. Phase 0 records baselines and may tighten them, but later work may not
weaken a threshold merely to make a change pass.

| Contract | Release gate |
| --- | --- |
| Identity and same-profile transforms | max `Delta E 00 <= 0.10`; alpha exact |
| ICC transform versus independent oracle | p95 `Delta E 00 <= 0.25`, max `<= 0.75` |
| ACES 2 SDR output versus pinned OCIO oracle | p99 `Delta E 00 <= 0.50`, max `<= 2.0` |
| Neutral-axis drift | max `Delta E 00 <= 0.20`; no visible chroma sign flip |
| CPU/GPU display transform parity | p99 `Delta E 00 <= 0.25`, max `<= 0.75` |
| Preview/final render parity | p99 `Delta E 00 <= 0.25` before output quantization |
| 8-bit encoded readback | max channel error `<= 1` code value for identity paths |
| 16-bit encoded readback | max channel error `<= 4` code values for identity paths |
| Real chart, supported camera/profile | median `Delta E 00 <= 2.0`, p95 `<= 4.0` after neutralization |
| HDR transform/reference parity | p95 `Delta E ITP <= 1.0`, max `<= 3.0` |
| Interactive first visible feedback | p95 `<= 50 ms` on the release reference Mac |
| Settled normal preview after a basic global edit | p95 `<= 250 ms`, or no worse than approved baseline |
| Memory | bounded by existing preview budgets; no full-frame duplicate introduced by output mapping |

Golden hashes remain useful for determinism, but a hash is never sufficient proof of color quality.

**Phase 0 status:** complete for the synthetic baseline. Real ICC profiles and measured camera/chart
fixtures enter in Phases 1, 2, and 5; Phase 0 does not claim they are already solved.

- CI reports perceptual percentiles, worst patches, neutral drift, and transform provenance.
- The baseline report is stored as an artifact; no production math changes are mixed into this phase.

  the same compiled/runtime/validated ICC capability state. The controller contract is covered by

- Strict CI and macOS/Windows release presets now build the official Little CMS 2.18 source archive

**Implementation progress (2026-07-14)**

- `OcioProjectConfig` is an immutable, explicit-only interoperability boundary. It accepts only a
  caller-selected `.ocio`, `.ocioz`, or `ocio://` source; it never reads the `OCIO` environment
  variable, installs a process-global config, or changes `default_color_pipeline_config()`. Desktop
  diagnostics publish backend/version availability and this isolation contract separately from the
  active photographic processor.
- Config inspection publishes content SHA-256, OCIO cache identity, strict-parsing state, roles,
  active color spaces, displays/views, looks, and ordered file rules. File-rule matching and
  color-space, display/view, look, CLF, and CTF processors are compiled only from an explicit
  request. Missing selections, unsupported sources, parse/validation failures, missing transforms,
  non-finite results, and changed alpha all fail closed without publishing partially transformed
  pixels.
- Context-variable resolution is deterministic and auditable. The loader clears values inherited
  from the process, restores only defaults declared by the selected config, then applies a
  duplicate-free caller override list. Config, processor, and GPU identities are derived from that
  sanitized context; inspection publishes each effective value as `config-default` or
  `explicit-override`. A pinned fixture proves that an ambient variable cannot redirect a LUT,
  while an explicit override changes the CPU result, dependency hash, and GPU program identity.
  Desktop diagnostics expose this as
  `config-defaults-plus-explicit-overrides` and `processEnvironmentIgnored: true`.
- Provenance hashing is streaming and memory-bounded. Standalone transforms retain their own
  content hash; virtual LUTs embedded in an `.ocioz` retain the containing archive hash and declare
  that provenance scope. Archive creation uses a non-overwriting partial file plus atomic rename,
  and the archived config is reopened and executed in the integration test.
- The pinned project fixture proves roles, displays/views, looks, file rules, signed/extended-range
  values, inversion, unassociated alpha, deterministic processor cache IDs, concurrent immutable
  processor reuse, standalone and config-relative CLF/CTF transforms, `.ocioz` round-trip, and a
  no-OCIO build that reports backend unavailability instead of silently changing behavior. The
  remaining Phase 8 completion gate is GPU parity for project-selected processors; these optional
  processors are not routed into the default preview or export path before that gate exists.
- Loaded configs now retain content identities for their source and every referenced transform
  actually used by a compiled processor. Source edits, archive replacement, deleted dependencies,
  and referenced-LUT edits invalidate the loaded object and require an explicit reload; a stale
  processor is never silently returned. The check is mutex-protected and passes ThreadSanitizer.
  Source files are hashed both before and after parsing, and standalone FileTransforms are hashed
  around compilation to close the common mutation window.
- `ocio_project_config_benchmark_driver` makes the cost contract repeatable. On the M4 Pro Release
  build with OpenColorIO 2.5.1, a cold config load is `0.82 ms`, repeated validated loads average
  `0.37 ms`, a cold processor compile is `0.18 ms`, integrity-checked repeated compilation averages
  `0.058 ms`, and a 262,144-pixel CLF application averages `0.64 ms`. OpenColorIO's own config
  processor cache is already effective, so the engine deliberately does not add a parallel wrapper
  cache that could preserve stale LUT data or split cache authority.
- Every validated project processor can now produce OpenColorIO's native MSL 2.0 GPU program from
  the exact same immutable processor used by the CPU path. The descriptor content-hashes the MSL,
  texture payloads, config, CPU processor, GPU processor, and OCIO shader identities; copies 1D,
  2D, and 3D resources into an immutable engine-owned contract; and rejects dynamic uniforms until
  their update lifecycle is implemented. Shader source is capped at 16 MiB, resources at 64
  textures and 256 MiB, and every size multiplication is overflow checked.
- The existing Metal backend dynamically compiles that MSL into its existing command queue, expands
  RGB LUT storage to native RGBA textures, binds OCIO-declared samplers, and keeps a bounded
  four-entry LRU keyed by complete program/resource identity. Results publish only after successful
  dispatch, finite RGB validation, and exact unassociated-alpha validation; failure leaves the CPU
  pixels untouched. Transfer/dispatch telemetry distinguishes first texture upload from cache reuse.
  The pinned fixture covers a pure signed/extended-range matrix program and a real 3D-LUT program.
  `metal_ocio_project_config_parity_test` enforces CPU/GPU channel and alpha tolerances and cache
  reuse on a Metal device. This host has no Metal device or offline `metal` compiler, so descriptor,
  source-contract, normal, sanitizer, and no-OCIO tests pass here while the actual hardware parity
  test correctly skips; the Phase 8 CPU/GPU completion gate therefore remains open.
- ACES2065-1/AP0 and ACEScg/AP1 now have explicit 16-bit half-float OpenEXR presets. Export applies
  a declared working-to-ACES D60 matrix to scene-linear floating-point samples, embeds the matching
  AP0/AP1 chromaticities and color-space name, preserves unassociated alpha and extended range, and
  records source/destination transform provenance. Fail-closed artifact inspection requires the
  requested ACES identity before a job may complete. Both formats re-enter the normal OpenEXR
  source path as tagged linear floating-point images, and integration proof compares AP1 readback
  against the exact declared matrix.
- The engine now owns an explicit AP1/D60 `ACEScct` identity plus the Academy's piecewise linear-to-
  log and log-to-linear equations, including the toe, negative values, over-range values, and the
  specified `65504` decode ceiling. Published equation vectors and round trips are executable
  gates. The OpenEXR writer deliberately rejects ACEScct, even as 32-bit float, because the
  [ACEScct specification](https://docs.acescentral.com/encodings/acescct/) says it is transient,
  defines no image container, and is not intended for interchange or archiving. This corrects the
  earlier roadmap assumption instead of inventing proprietary metadata under a standards-looking
  preset.

**Completion gate**

- OCIO CPU/GPU processors agree within tolerance for pinned reference configs.
- Missing configs or transforms fail explicitly; no asset is silently treated as a color image or
  as sRGB.

## Definition of “industry leading”

The color engine earns that description only when all P0/P1 phases are complete and proven:

- real profiles are parsed rather than simulated;
- RAW input is characterized once, at a known boundary;
- scene grading and display rendering are separate;
- SDR, HDR, proof, and export targets are explicit;
- preview and export match within perceptual thresholds;
- CPU and GPU match within perceptual thresholds;
- representative real cameras and photographs pass measured and editorial gates;
- old recipes remain reproducible;
- the normal editing path remains visibly immediate and memory-bounded.
